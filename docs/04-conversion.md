## Stage 1: extract_weights.py

**Purpose**: Read 46 shards, extract non-expert tensors, write to single `model_weights.bin`.

### Execution

```bash
cd /Volumes/FlashMoE/flash-moe

/Users/migi/flashmoe_venv/bin/python scripts/extract_weights.py \
  --model-dir /Volumes/FlashMoE/models/mlx-community-Qwen3.5-397B-A17B-4bit \
  --output /Volumes/FlashMoE/models/mlx-community-Qwen3.5-397B-A17B-4bit/model_weights.bin
```

### Expected runtime

Based on Flash-MoE docs: "Depends on disk speed, typically 10-30 minutes for a 200GB+ model."

### Actual runtime

```

  shard 2/46: done
  ...
  shard 46/46: done
Writing manifest...
Total time: 2.1 seconds
```

**2.1 seconds.**

Expected 10-30 minutes → got 2.1 seconds.

### What actually happens

extract_weights.py logic:

1. Opens `model.safetensors.index.json` to know which tensors are in which shard
2. For each non-expert tensor:
   - Parses header of relevant shard (tiny, not full file read)
   - Memory-maps just that tensor's bytes
   - Writes to output file
3. Builds manifest

**Key insight**: We don't read all 224GB. We only read the non-expert tensors (~5.5GB total).

Via mmap + sparse reading, this can be very fast on SSD.

## Stage 2: repack_experts.py

**Purpose**: Read 46 shards, extract expert weights, repack into per-layer files.

### Execution

```bash

  --output-dir /Volumes/FlashMoE/models/mlx-community-Qwen3.5-397B-A17B-4bit/packed_experts \
```

**81.5 seconds for 202 GB.**

Expected: 1-2 hours based on docs. Got: 1 minute 21 seconds.

### Why so fast

This is I/O bound, and TB5 NVMe SSD delivers:
- Read from shards: ~3-4 GB/s
- Write to packed: ~2.5-3 GB/s
- Total process: ~2.5 GB/s sustained (bottleneck = write speed)

Flash-MoE's repack is essentially memory copy with rearrangement. No CPU-heavy work. So disk speed dominates.

Modern SSDs are incredibly fast for this workload.

## Space cleanup decision

At this point, we have:
- Original shards: 224GB
- Packed experts: 202GB
- Extracted weights: 5.5GB
- **Total: 431GB on 447GB SSD**

Only 16GB free. Risky.

**Options**:

1. Delete original shards (saves 224GB)
   - Pro: massive space savings
   - Con: can't re-convert if something is wrong

2. Keep originals
   - Pro: re-conversion possible
   - Con: tight space

Chose **option 2**. Kept originals as backup until Phase 7 verified the conversion works.

Later (after Phase 9 migration), moved originals to archive role on external.

## Why estimates were wrong

Flash-MoE's docs said "typical 10-30 minutes." Our result: <2 minutes.

Probably because:
- Docs written for older/slower NVMe
- Or conservative to avoid "why is it slow?" complaints
- Or tested on slower CPUs

At 4+ GB/s sustained IO on Apple Silicon + TB5 NVMe, this operation is effectively disk-speed-limited. Not CPU-bound.

**Lesson**: Always time a test case first. Don't plan schedules based on max-estimate.

## Lessons

1. **Don't trust time estimates in docs.** Always test.
2. **Modern SSDs are fast.** I/O bound workloads complete quickly.
3. **Verification matters.** --verify flag caught zero errors, but finding one would have saved hours.
4. **Keep originals until verified.** Space permitting, backup until pipeline confirmed working.
5. **Conversion is the easy part.** Debugging runtime was where real time went.
